### Deviation note (D-11, user decision 2026-11-19)

AGENTS.md says not to create parallel tables and to search existing first. The search found a live `public.employees` table, but it is internal-use only: it has no `client_id`, RLS is on with zero policies, it holds no rows, and other internal tables point at it. It cannot serve tenant staff and must not be altered, reused or referenced. The user therefore decided to create a new tenant-scoped `staff_members` table. This knowingly deviates from the "no parallel tables" rule, because the existing table is internal-only; the deviation is recorded in the INTEGRATIONS and CONCERNS docs updated in Task 2 so future work does not merge the two by accident.

## 1. Cross-cutting conventions (apply to every task)

- **C-1 Migrations.** Files `supabase/migrations/YYYYMMDD_snake_description.sql`, numbered after the newest existing file (20261117_drop_communication_tables): this plan uses 20261119 to 20261121. Additive and idempotent (`if not exists`, `drop policy if exists` then create). Header comment states: authored, not applied, apply by hand in the SQL Editor (never CLI push), apply BEFORE deploying code that reads the table (tab-access seed files are the exception: applied LAST). Live default privileges hand new tables to `anon`, so every table gets `revoke all ... from public, anon, authenticated` then an explicit minimal `grant ... to authenticated`. RLS enabled. The own-client predicate is `clients.crm_user_id = auth.uid()` for the row's client, expressed through `public.crm_can_access_client(client_id)` when probe P-4 confirms that function is exactly that check (it is what every existing own-client policy uses), otherwise as an explicit exists-subquery against `clients`. Commented read-only verification queries, a commented rollback block, and rolled-back role-simulation probes (cross-tenant, anon) go at the bottom, as in 20261108 and 20261112. Reuse `public.update_updated_at_column()` for `updated_at` triggers (exists live, search_path pinned by 20261108).
- **C-2 Tenancy.** Browser: `clientId` comes from `useClient()` and goes first into every query function; every query has `.eq("client_id", clientId)`; `client_id` is written after any payload spread. Server routes: tenant comes only from `getAuthenticatedRequestClient(authorization)`; never from body, query string or URL. RPCs take `p_client_id` and still run the own-client check first. The OAuth callback has no bearer token, so its tenant comes only from the server-stored state row created under an authenticated session. The cron route has no tenant at all (it drains by claim function).
- **C-3 Module pairs.** `{domain}-types.ts` plus `{domain}-queries.ts` in `src/lib`, local `getClient()`, `raiseQueryError` wrapping `formatSupabaseError`, named exports, `clientId` first argument. Hooks in `src/hooks/use-{name}.ts` return `{ data, loading, saving, error, refresh, mutators }`. Provider code in `src/lib/providers/google-calendar/`. Server-only helpers in `src/lib/server/`, each marked server-only by living there and never imported from `"use client"` files.
- **C-4 Pure modules.** Anything with business math (client settings parsing, reminder window, package ledger, calendar event mapper) is import-free and uses only erasable TypeScript, following `appointment-schedule.ts`, so Node 24 can load it directly from `scripts/check-*.mjs` assertion scripts (the repo has no test runner; do not add one). Server code reuses the same pure modules through `@/` imports. The cron auth helper imports only Node's `crypto`, so it is loadable the same way.
- **C-5 Errors and logs.** Query modules wrap errors with user-facing fallbacks; RPC errors are mapped by SQLSTATE like `mapCreateBillError` in `clinic-billing-queries.ts`. Route handlers: try/catch, `NextResponse.json({ error }, { status })`, substring status mapping as in the existing notification route, no stack traces. Server logs use the `[integration-sync]` prefix via `console.error`, never tokens, auth codes, secrets, response bodies or patient data.
- **C-6 UI.** `DataState` for loading/error/empty, `EntityModal` for forms, `cn()`, theme tokens, 44px touch targets with the existing `min-h-11 xl:min-h-0` pattern, usable at 320px. `appointments-tab.tsx` is already very large: new UI goes in extracted components, the tab only gains thin wiring.
- **C-7 Tab wiring contract.** A new real tab (Staff in Wave 1, Packages in Wave 3) needs: default-exported client component with `{ clientId }`, dynamic import and render line in `dashboard-page.tsx`, key in `DASHBOARD_TAB_ROUTES`, DB key mapping in `DB_KEY_TO_CODE_KEY` (and `DEFAULT_TAB_ORDER` if it should sort), a `tabs_info` seed migration (plus a `client_tab_access` backfill where the feature should appear automatically), and an `existing-tab` navigation item in `module-navigation.ts` (the item shows only when the tenant has the tab). Tab numbers: 027 Staff, 028 Packages, 029 Calendar-sync (an access-only key with no screen, like the LEADS and HRM gates). HRM keys 023 to 026 and the `hrm-*` navigation items are not touched by any task.

### 5.2 Session state machine and credit math

| Status | Meaning | Consumes credit | Holds a slot |
|--------|---------|-----------------|--------------|
| scheduled | Linked to an appointment, outcome unknown | no | yes |
| completed | Appointment completed | yes | no |
| missed_pending | Cancelled or marked missed, awaiting doctor decision | no | yes |
| rolled_over | Missed, doctor kept the credit | no | no |
| forfeited | Missed, doctor forfeited the credit | yes | no |
| voided | Link removed or package cancelled | no | no |

- Consumed = completed + forfeited. Held = scheduled + missed_pending. Remaining bookable = total minus consumed minus held; attach is rejected when it would go below zero. Rolled-over credit needs no separate record: it simply is not consumed, so remaining increases and the customer books a new appointment (a new session row). A package becomes completed when consumed reaches total.
- Transitions are driven by a SECURITY DEFINER trigger on `appointments` (after update of `status`): to completed marks the linked session completed; to cancelled marks a scheduled session missed_pending; back from cancelled to booked or tentative reverts an unresolved missed_pending to scheduled (a resolved decision is never reverted). A trigger covers every UI path that changes status (modal, calendar quick action, summary). It must not swallow errors: a failed ledger write must roll back the status change so credit and appointment never disagree.
- "Prompted each time": the missed-session dialog opens right after the UI sets a linked appointment to cancelled, and from an explicit "Mark missed" action on overdue scheduled sessions. The default radio is the tenant `missed_default` (rollover unless changed); choosing the other option stores `resolution_overrode_default = true`. Dismissing the dialog leaves the session missed_pending, which never consumes credit and re-surfaces as a Needs decision badge on the Packages and Appointments tabs.
- Payment math (`package-ledger.ts`): upfront balance = price_total - paid; installments: scheduled due to date = sum of installments with due_on <= today in the clinic time zone, overdue = max(0, due to date - paid), total balance = price_total - paid; per_visit: accrued = price_per_session x consumed (forfeited sessions accrue, completed sessions accrue, rolled over do not), balance = accrued - paid.

### 6.3 Enqueue and reconcile design

- Trigger `appointments_integration_outbox` (AFTER INSERT, UPDATE, DELETE) is SECURITY DEFINER with pinned search_path. It enqueues only when a connected integration exists for `client_id` and (on update) a synced column changed: date, start_time, end_time, status, service, location, staff_member_id, staff_name, deleted_at. Insert uses `on conflict do nothing` against the pending partial index, so any burst of edits coalesces into one pending row. It must never block the appointment write: body wrapped so an enqueue failure raises a warning only (missing events are repaired by resync, Task 10).
- The outbox row carries only entity type and id. The worker reads the appointment fresh at send time and computes the desired state: absent (row missing, deleted_at set, status cancelled, or no start_time) or present (payload). It compares against the link: absent with link means delete event; present without link means insert; present with changed hash means patch; unchanged means done. Ordering, duplicates and retries are therefore harmless (at-least-once with idempotent effects).
- Event ids are deterministic base32hex (characters a to v and 0 to 9, 5 to 1024 chars): first 26 chars of base32hex(sha256 of connection id, appointment id, generation). Insert collision (409) means GET then patch (and patch status back to confirmed if the event was cancelled). Patch or delete returning 404 or 410: delete is treated as success; patch re-inserts with generation + 1.
- Initial backfill on connect and full resync on time zone change: enqueue upcoming appointments (date from yesterday on, not deleted, not cancelled, has start_time), batches of 500, capped at 2000 per run.

### 6.4 Mapper and privacy (D-08)

`event-mapper.ts` is pure. Its input type contains only `id, date, start_time, end_time, status, service, location, staffName` plus settings and time zone, so name, phone, email and remark cannot reach the payload by construction.

| Field | Value |
|-------|-------|
| summary | `calendar_sync.title_template` with `{service}` and `{staff}` replaced; default `Appointment` |
| start / end | wall-clock `YYYY-MM-DDTHH:mm:00` plus `timeZone` from `scheduling.timezone` (appointment times are stored as time without time zone, assumption A-01 resolved 2026-11-10); missing or non-increasing end becomes start plus 30 minutes (`DEFAULT_APPOINTMENT_MINUTES`) |
| location | only when `include_location` is on |
| status | tentative maps to tentative; booked and completed map to confirmed; cancelled or deleted means the event is deleted |
| extendedProperties.private | one reference key holding the appointment id (needed to repair links); no other data |

### 6.9 Scheduler: pg_cron plus pg_net (D-12; P-7 resolved)

Facts checked against Supabase docs on 2026-11-19: pg_net is async and sends only after the transaction commits, `net.http_post(url, body, params, headers, timeout_milliseconds)` defaults to a 2000 ms timeout, stores responses in `net._http_response` for 6 hours by default (changing the TTL needs Supabase Support), uses unlogged tables so queued requests can be lost on a crash, is documented as beta and targets up to about 200 requests per second; pg_cron wants at most 8 concurrent jobs of at most 10 minutes each; Vault exposes plaintext through `vault.decrypted_secrets`, so access to that view must be restricted.

**Migration `20261121_integrations_cron.sql` (authored in Task 10, applied by hand after the route is deployed):**

| Part | Content |
|------|---------|
| Extensions | Enable pg_cron, pg_net and (if probe P-5 says it is missing) Vault, each in the schema Supabase documents for the project's Postgres version; header notes extension enablement needs the `postgres` role in the SQL Editor |
| Wrapper function | `public.integration_cron_drain()` SECURITY DEFINER, pinned search_path, fully qualified `vault.` and `net.` calls; reads `integration_cron_secret` and `integration_app_url` from Vault; raises an exception (so the job run shows failed) when either is missing, blank or the URL is not https; calls `net.http_post` to the app URL plus `/api/cron/drain` with header `x-integration-cron-secret`, an empty JSON body and `timeout_milliseconds` of 10000; execute revoked from public, anon, authenticated; no secret ever appears in the file |
| Drain job | `cron.schedule` job named `integration-outbox-drain`, schedule every minute, command calls the wrapper; the job only enqueues an async request, so it finishes in milliseconds and never overlaps itself |
| Housekeeping job | Daily job: delete `cron.job_run_details` rows older than 7 days (one row per minute otherwise grows without bound), delete `integration_outbox` rows with status done older than 7 days and dead older than 90 days, delete expired `integration_oauth_states` |
| Footer | Commented read-only queries: recent `net._http_response` rows (status_code, timed_out, error_msg, created), `cron.job` and recent `cron.job_run_details`; rollback block (unschedule both jobs, drop wrapper) |

**Secrets:** the cron secret and the app URL are created by hand in Vault (user_setup), never in git or migrations. The same secret value is set as `INTEGRATION_CRON_SECRET` in Vercel. Rotation runbook: set the new value in Vercel and Vault together; between the two changes the route answers 401, which shows in `net._http_response` and self-heals on the next minute once both match.

**Route `POST /api/cron/drain`:** Node runtime, `dynamic = "force-dynamic"`, an explicit `maxDuration` within the Hobby limit (verify current limit), a per-run cap of jobs and an 8 s work budget. The cron auth helper hashes the provided header value and the expected secret with SHA-256 and compares the digests with `timingSafeEqual` (fixed length, so neither content nor length leaks), and fails closed: unset or empty expected secret, missing header, any mismatch gives 401 with no detail. Responses carry counts only (claimed, succeeded, failed, dead), never tenant data, because response bodies sit in `net._http_response` for 6 hours.

**Idempotency under overlap:** a pg_net timeout cancels the waiting, not the Vercel function, so a "timed out" run may still be working when the next minute fires. This is safe: the claim function uses `for update skip locked` plus a 5 minute lease, so overlapping runs get disjoint rows; a crashed run's rows are re-claimed after the lease; each job is idempotent (deterministic event id, payload hash compare, desired-state reconcile). No global lock is used, so one slow run never blocks the next.

**Failure modes:**

| Failure | Effect | Handling |
|---------|--------|----------|
| App URL unreachable, DNS failure, 5xx | pg_net records the error; nothing is claimed | Next minute retries on its own; rows stay pending; card shows Sync delayed after 10 minutes |
| Cold start slower than the pg_net timeout | Response recorded as timed out although the function runs | 10 s timeout covers normal cold starts; overlap is safe (above) |
| Wrong or rotated secret | Route returns 401 | Visible in `net._http_response`; rotation runbook above |
| Vercel deployment protection answers instead of the app | 401 or 403 from Vercel, not from our route | Target the production custom domain, or add Vercel's automation bypass header to the wrapper (verify in Vercel docs) |
| Vault secret missing or URL not https | Wrapper raises, job run marked failed | Visible in `cron.job_run_details`; fix Vault entries |
| pg_net queue lost on crash | A few minutes of missed ticks | Next tick drains the backlog; rows are durable in the outbox table |
| Extensions not enabled or cron job removed | No ticks | Nudge still drains per tenant on appointment saves; Sync delayed state surfaces it |
| Drain slower than the per-run cap | Backlog | Leftover rows wait for the next minute tick |

Local development: pg_net cannot reach localhost, so call the cron route with curl using the local secret, or rely on the nudge. Preview deployments are not scheduler targets.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser to PostgREST | Authenticated tenant user, any client_id they type; only RLS and grants protect rows |
| browser to Route Handlers | Bearer token identifies one tenant; body and query are untrusted |
| Google redirect to callback | No bearer; trust only a server-stored single-use state row |
| pg_cron and pg_net to cron route | Public internet request carrying a shared secret header; no tenant context |
| Supabase Vault to wrapper function | Plaintext secret and app URL read inside a definer function |
| server to Google | Tokens and appointment-derived data leave the system |
| DB definer functions and triggers | Run with elevated privilege on behalf of the caller |
| staff_members versus the internal employees and people tables | Must stay fully separated; tenant code never touches the internal tables |
| tab access seed migrations to client_tab_access | Admin-run SQL writes navigation rows for many tenants at once |
